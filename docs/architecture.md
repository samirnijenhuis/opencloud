# Opencloud architecture

This document is the contract for the code. The design document `docs/superpowers/specs/2026-10-22-opencloud-design.md` says what opencloud does and why. This document says where each part lives and how the parts talk. When the code and this document disagree, fix one of them in the same commit.

## Repository layout

| Path | Contents |
|---|---|
| `install.sh` | The one-command installer for a fresh Ubuntu 24.04 server. |
| `bin/opencloud` | The CLI that the installer puts on the server, for example `opencloud upgrade`. |
| `platform/` | Kubernetes manifests for the opencloud parts on the `local` cluster. `platform/images/caddy/` holds the Caddy image. |
| `dashboard/` | The Laravel app. It is the dashboard, the API, and the queue worker. |
| `dashboard/app/` | The PHP code in five folders: `Console`, `Domains/<Domain>`, `Http`, `Providers`, and `Support`. `.claude/rules/architecture.md` lists the domains and says what goes in each folder. |
| `dashboard/Dockerfile` | The image of the dashboard. CI publishes it. |
| `dashboard/resources/docker/` | The Dockerfile templates of the Laravel, Node.js, and static presets. |
| `dashboard/resources/ssh/github_known_hosts` | The pinned SSH host keys of github.com, for git over SSH with a deploy key. |
| `tofu/` | OpenTofu modules for `created` clusters and managed services. |
| `tests/e2e/` | The release test. It drives a fresh Ubuntu machine end to end. |

## Names

Use these names everywhere: in PHP, in the UI, in Kubernetes labels, and in docs.

| Name | Meaning | Not |
|---|---|---|
| `Application` | One GitHub repository that opencloud deploys. The model is `App\Domains\Applications\Models\Application`. | `App`, because `App\` is the PHP root namespace. |
| `Environment` | One running copy of an application, for example production or a preview. | |
| `Process` | One command of an environment next to web. A long-running process, for example a queue worker, runs all the time. A scheduled process, for example a cleanup script, runs on a cron schedule. The model is `App\Domains\Environments\Models\Process`. | `Worker`, because a queue worker is only one kind of process. |
| `Deployment` | One attempt to put one commit live in one environment. | |
| `Datastore` | A database, Valkey, or RustFS server that opencloud runs. | `Service`, because a Kubernetes `Service` is a different thing. |
| `DatastoreAttachment` | One environment's database, user, bucket, or key on a datastore. | |
| Connection name | The name of one MySQL or Postgres attachment, for example `main` or `reports`. The app uses it as the name of a Laravel connection. | |
| Default database | The one MySQL or Postgres attachment of an environment that sets the `DB_*` values. | |
| Bucket name | The name of one bucket attachment, for example `main` or `uploads`. A Laravel app uses it as the name of a disk. | |
| Default bucket | The one bucket attachment of an environment that sets the `AWS_*` values without a prefix. | |
| Public bucket | A bucket attachment with `is_public` set. Anyone can read a file at its public address without a key. Nobody can list, upload, or delete without the key. A bucket is private by default. | |
| `Cluster` | A Kubernetes cluster that runs environments and datastores. | |
| `ProviderCredential` | An API key for a cloud provider or Cloudflare. | |

## The local cluster

The installer creates this layout on the dashboard VPS. All opencloud parts live in the namespace `opencloud`.

| Part | Kind | Address |
|---|---|---|
| Dashboard | One pod with three containers, `web`, `worker`, and `scheduler`. They share the host path `/var/lib/opencloud/data`, which holds `database.sqlite`. | Service `dashboard.opencloud.svc.cluster.local:8080` |
| Caddy | Deployment `caddy` with a rolling update, Service `caddy` of type `LoadBalancer` with ports 80, 443, and 8000. k3s ServiceLB binds these ports on the host. Certificates and the last config live on the host paths `/var/lib/opencloud/caddy/data` and `/var/lib/opencloud/caddy/config`, so they survive a pod restart. | Admin API on `127.0.0.1:2019` inside the pod only |
| Registry | Deployment `registry` with the image `registry:3`, data on the host path `/var/lib/opencloud/registry`. | Service `registry` with the fixed ClusterIP `10.43.200.200`, port 5000 |
| BuildKit | Deployment `buildkitd`, privileged, state on the host path `/var/lib/opencloud/buildkit`. | No Service. BuildKit listens only on the Unix socket `/run/buildkit/buildkitd.sock` in its pod, and the dashboard runs `buildctl` there through `kubectl exec`. |

Images have names like `registry.opencloud.svc.cluster.local:5000/<application-id>/<environment-id>:<short-sha>-<deployment-id>`. BuildKit pushes to that name over plain HTTP, because it resolves cluster DNS. The node cannot resolve cluster DNS, so the installer writes `/etc/rancher/k3s/registries.yaml` with a mirror from that name to `http://10.43.200.200:5000`. The registry is never reachable from outside the cluster.

The dashboard runs `kubectl` with its in-cluster service account for `local`. The service account has `cluster-admin` on `local`.

The NetworkPolicies in `platform/networkpolicies.yaml` let only the dashboard reach BuildKit, and only the dashboard and BuildKit reach the registry. The node still pulls through the registry ClusterIP, because kube-router lets traffic from the node itself reach local pods. `tests/e2e/network-policy.sh` proves both.

A release is a tag `v*`. `.github/workflows/release.yml` publishes the dashboard image and the Caddy image (`opencloud-caddy`) for amd64 and arm64 and a release archive with `install.sh`, `platform/`, and `bin/`. `tests/e2e/build-release-archive.sh` builds the archive for the workflow and for the tests. When `install.sh` runs from `curl | bash`, it downloads that archive, checks its SHA-256 sum, extracts it to `/opt/opencloud/<version>`, and runs from there. Without `OPENCLOUD_VERSION`, it asks the GitHub API for the tag of the latest release and installs that tag, so the dashboard always knows its real version. The dashboard image builds on the exact tag `dunglas/frankenphp:1.13.2-php8.5.12`, so a local build cannot reuse an older cached image with a moving tag. PHP 8.5.12 is the first 8.5 release that fixes PHP2Shell (CVE-2026-109618 and CVE-2026-109619). A new PHP patch needs a change of this tag.

The installer keeps its state in `/var/lib/opencloud`. The files `APP_KEY` and `setup-token` there have mode 600. The installer copies them into the Secret `dashboard` and never into a manifest file. The k3s options live in `/etc/rancher/k3s/config.yaml`. If `APP_KEY` is missing while the database exists, the installer stops, because a new key cannot read the stored secrets. In restore mode, the installer brings both back from the backup bucket. The section Restore describes it.

The dashboard is at `http://<server-ip>:8000`. Caddy forwards port 8000 to the dashboard Service. The owner can also give the dashboard a domain in Settings. After its DNS check passes, Caddy serves the dashboard on that domain over HTTPS, and the dashboard uses the domain as its root URL. The queue workers restart then, because they read the root URL when they boot.

## How the dashboard talks to a cluster

`App\Support\Kube\Kubectl` is the only class that runs `kubectl`. It runs the binary with Symfony Process. For `local` it uses the in-cluster config. For other clusters it writes the decrypted kubeconfig to a temporary file for the duration of one call. Tests bind `App\Support\Kube\FakeKubectl`, which records each call and returns scripted output.

Manifests are plain PHP arrays that pure classes build from models. Each domain keeps its manifest class, for example `App\Domains\Deployments\EnvironmentManifests`, and `App\Support\Kube\Labels` holds the shared labels. `Kubectl::apply()` sends them with `kubectl apply --server-side --force-conflicts --field-manager=opencloud`. The same apply gives the same result when it runs again, so each sync sends the full desired state.

Each environment gets its own namespace, `oc-env-<environment-id>`. Datastores live in the namespace `oc-datastores`.

## How the dashboard talks to Caddy

`App\Domains\Routing\CaddyConfig` is a pure class. It builds the full Caddy JSON config for one cluster from the database. `App\Domains\Routing\CaddySync` sends that JSON to the Caddy pod with `kubectl exec`. Inside the pod it posts the JSON to `http://127.0.0.1:2019/load`. Use `127.0.0.1`, not `localhost`. Busybox resolves `localhost` to `::1`, and Caddy does not listen there. Caddy applies a config completely or rejects it.

Caddy runs with `--resume`, so it keeps the last config when it restarts. The scheduler also sends the full config every five minutes, so drift repairs itself.

A domain goes into the Caddy config only after its DNS check passes. Caddy then gets the certificate with its normal automatic HTTPS. Opencloud does not use on-demand TLS, because the dashboard always knows each hostname before Caddy needs it. Each minute, `CheckCertificates` makes a TLS handshake with the ingress for each domain whose DNS check passed. It stores `issued` when the certificate names the domain and is valid now, and `pending` otherwise. The handshake does not check the CA, so a certificate of the local CA counts. The Caddy image is the official Caddy of the same version plus the module `github.com/caddy-dns/cloudflare`, built with xcaddy in `platform/images/caddy/Dockerfile`. `install.sh` imports it from `OPENCLOUD_CADDY_IMAGE_ARCHIVE` or pulls it from `ghcr.io`.

A domain in `cloudflare` DNS mode needs the Cloudflare key. Opencloud creates the A record through the Cloudflare API, and `CaddyConfig` puts the hostname under a TLS automation policy with the Cloudflare DNS challenge and the stored token. That policy comes before the policy without subjects. Removing the domain deletes the record that opencloud created. The certificate issuer comes from the setting `OPENCLOUD_TLS_ISSUER`. The value `acme` uses Let's Encrypt. The value `internal` uses the local Caddy CA, for tests.

## Provider keys

`App\Domains\CloudProviders\Providers` is the one table of provider guides: DigitalOcean, Hetzner, AWS, and Cloudflare. Each `ProviderGuide` has the key page URL, the rights to select, an optional CLI command, and a check class. A check makes read-only API calls and returns a `CheckResult` with the status `ok`, `invalid`, or `missing_rights`. The DigitalOcean guide lists two optional rights, because a cluster works without them: `database` for managed Postgres and Valkey, and `spaces_key` for a Spaces bucket. Its check probes `/databases` and `/spaces/keys`. A stored key that lacks a right does not offer the resources that need it, because `ManagedResource::refusalOn()` reads `missing_rights`. The Hetzner and AWS guides only store and check a key. No feature uses these keys yet. The AWS check signs its requests with `AwsSignatureV4`. The settings page "Provider keys" is for the owner only. The command `opencloud:check-provider-links` requests each key page, and a weekly workflow runs it.

## OpenTofu

`App\Support\Tofu\Runner` is the only class that runs `tofu`. A `Stack` names a module under `tofu/`, a work folder `<data_path>/tofu/<kind>-<id>`, the module variables, and the provider credentials. Each run copies the module into the work folder and writes the variables to `opencloud.tfvars.json` with mode 600. The token goes into the process env only, for example `DIGITALOCEAN_TOKEN`. The state stays in the work folder, and `TF_ENCRYPTION` always turns on state and plan encryption with a PBKDF2 passphrase from `APP_KEY`. So the passphrase is never on disk, and a new `APP_KEY` cannot read the old state. Each output line goes through `SecretMasker` into the `tofu_log` column, which the owner sees in the UI. The outputs never go into the log. Tests swap `tofu` with `Process::fake()`. `StateEncryptionTest` runs the real binary when `OPENCLOUD_TEST_TOFU_BINARY` is set.

The image holds a pinned `tofu` and the modules in `/opt/opencloud/tofu`. Build it with `--build-context tofu=tofu`. The `.terraform.lock.hcl` of each module pins the provider hashes.

- `tofu/digitalocean/cluster` creates a DOKS cluster with one autoscaling node pool. It uses the registry of the account and creates one when the account has none. The registry has `destroy = false`, so a destroy leaves it for other clusters. The module outputs a kubeconfig with a service account token, because the kubeconfig of DigitalOcean expires after seven days, and a credential for the registry only.
- `tofu/digitalocean/database` creates a managed MySQL or Postgres with one node, a database, and a user. Its firewall lets in only the Kubernetes cluster.
- `tofu/digitalocean/valkey` creates a managed Valkey with one node in the VPC of the cluster. Its firewall lets in only the Kubernetes cluster. The attachment stores the private host, the port, the password, and `tls`.
- `tofu/digitalocean/spaces-admin-key` creates a Spaces key with full access, for OpenTofu only.
- `tofu/digitalocean/bucket` creates a Spaces bucket and a key with readwrite on that bucket only. The provider creates a bucket through the S3 API, and that API needs a Spaces key. A provider cannot take its credentials from a resource of the same apply. So `ManagedBucket` applies `spaces-admin-key`, gives its key to `bucket` in the process env, and destroys `spaces-admin-key` at the end of every run, so no full-access key stays in the account between runs. A destroy runs in the order `spaces-admin-key` apply, `bucket` destroy, `spaces-admin-key` destroy. A failed bucket step also destroys the admin key and keeps its own error. A new key may not work on the S3 API at once, so the bucket step runs again, up to 5 tries with 10 seconds between them, but only for an error about an unknown access key. A run that stops between the steps converges on the next run. The app gets only the bucket key, and a detach deletes the bucket and its files.

A cluster provider is a class that implements `App\Domains\Clusters\ClusterProvider`. `App\Domains\Clusters\ClusterProviders` lists the providers and finds one by the value of `clusters.provider`. The provider names the credential that it needs, and it owns the choices of the create form: regions, node sizes, the node limit, and the pricing link. It also builds the OpenTofu stack of a cluster and maps the stack outputs to the cluster columns. `ProvisionCluster`, `TearDownCluster`, `CreateCluster`, the form request, and the cluster pages read only this interface. The create route is `clusters/create/{provider}`, and the list page shows one Create button for each provider. DigitalOcean is the only provider today. To add one, write one class, add one OpenTofu module under `tofu/`, and add the class to the list in `ClusterProviders`.

`CreateCluster` stores a `created` cluster with the status `provisioning`. `ProvisionCluster` applies the cluster module, stores the kubeconfig and the registry, and dispatches `InstallClusterParts`. `DestroyCluster` refuses while applications or managed resources use the cluster, and `TearDownCluster` runs `tofu destroy` and removes the record. A managed attachment has a managed `Datastore` of its own. `ProvisionManagedDatabase` has `ManagedResource` apply the stack of its kind. Then `AttachmentEnv` writes the env values, the same as for a standard attachment. Detach of a managed attachment runs `TearDownManagedDatabase`, which destroys the resource and its data. Both jobs serve every managed kind and keep their names, so jobs in the queue still run. The OpenTofu jobs run on the `builds` queue, because a cluster or a database takes minutes. A failed run keeps the record with the error, and the next run converges.

## Builds

An application has a preset. The column `applications.type` stores it, and `App\Domains\Applications\Enums\ApplicationType` casts it. The presets are `laravel`, `node`, `python`, `ruby`, `static`, and `dockerfile`. The enum holds each default of a preset: the port, whether the user can change the port, the health path, the processes, the deploy commands, whether the build command applies, the database, the env profiles, the system env values, and the generated secrets. `CreateApplication`, `OpenPreview`, `EnvironmentVariables`, and the create form read them from the enum. `Builder::prepare()` picks the Dockerfile by the preset and never changes the preset. When a repository does not fit its preset, the build fails with a plain message. `DockerfileTemplate` fills each template.

The build command is one text with a command on each line, and the deploy commands are a list. `StoreApplicationRequest::cleanLines()` and `cleanScript()` drop each empty line and each comment line (a line that starts with `#`) before the request validates, so the stored values hold only commands. `DockerfileTemplate::run()` writes the build command into every preset template as one `RUN` heredoc with `set -e`, so the build stops at the first command that fails and a newline cannot end the instruction. BuildKit v0.25.1 supports the heredoc together with the secret mounts. The create form and the environment settings page edit both fields in `ShellEditor`, a textarea with shell highlighting.

The user chooses the preset when the application is created. It cannot change afterward, because a preset brings its own processes, deploy commands, port, and secrets, and a change leaves a mix that fails. `RepositoryDoesNotFit` ends each message for a repository that does not fit its preset with "To use another preset, create a new application with the same repository." `RepositoryFiles` reads the clone for the Python and Ruby presets. `RuntimeVersion` turns a version or a range into an image tag. A full version x.y.z picks that exact image, a minor x.y picks its newest patch, and a range picks the default or the highest minor that it allows.

- `LaravelDockerfile` fills `laravel.Dockerfile` from `composer.json` and `package.json`. The image runs FrankenPHP on port 8080 and serves `/app/public`. The PHP minor comes from `require.php` in `composer.json`. The list `opencloud.php_versions` holds 8.2, 8.3, 8.4, and 8.5, each on the moving FrankenPHP tag `1-php<minor>`, so each build gets the newest patch of that minor. The build takes `LaravelDockerfile::DEFAULT_PHP`, 8.4, when the range allows it, and else the highest listed minor that the range allows. So a new minor in the list does not move an app with `^8.2`, whose lock file can hold a package that does not support the new minor yet. An app opts in with a range such as `^8.5` or `~8.5.0`.
- `NodeDockerfile` fills `node.Dockerfile`. `NodeProject` takes the Node version from `engines.node`, with Node 24 as the default, and picks npm, pnpm, or yarn by the lock file. The image runs the build script and the build command, and it starts with the start script or `main`.
- `StaticDockerfile` fills `static.Dockerfile`, where nginx serves port 8080. When `package.json` has a build script, a build stage runs it, and nginx serves the output folder.
- `PythonDockerfile` fills `python.Dockerfile` on the full `python` image. `PythonProject` picks the tool by the first of `uv.lock`, `poetry.lock`, `Pipfile.lock`, `requirements.txt`, and `pyproject.toml`. The dependencies go into `/opt/venv`, without the dev dependencies. The version comes from `.python-version`, the Pipfile, or `requires-python`, with Python 3.14 as the default. The app starts with the `web:` line of its `Procfile`, else with gunicorn or uvicorn for a Django, Flask, or FastAPI app.
- `RubyDockerfile` fills `ruby.Dockerfile` on the full `ruby` image. It runs `bundle install` without the development and test groups. A Rails app with Propshaft or Sprockets runs `bin/rails assets:precompile` with `SECRET_KEY_BASE_DUMMY=1`. The version comes from `.ruby-version` or the `ruby` line of the Gemfile, with Ruby 3.4 as the default. The app starts with the `web:` line of its `Procfile`, else with `bin/rails server`, else with puma or rackup for a `config.ru`.
- The `dockerfile` preset builds the `Dockerfile` of the repository.
- The Node.js, Python, and Ruby images run `tini` as PID 1, so the app gets SIGTERM when a pod stops.

A Laravel app gets the system env values `APP_ENV`, `APP_DEBUG`, `LOG_CHANNEL`, and `APP_URL`. Every other preset gets `PORT` with the application port, and `APP_URL`. A Node.js app also gets `NODE_ENV=production`. A Python app also gets `PYTHONUNBUFFERED=1`, `DEBUG=false`, `ALLOWED_HOSTS` with the domains of the environment, and a generated `SECRET_KEY`. A Ruby app also gets `RACK_ENV`, `RAILS_ENV`, `RAILS_LOG_TO_STDOUT`, `RAILS_SERVE_STATIC_FILES`, and a generated `SECRET_KEY_BASE`. The preset does not know the framework, so every Python app gets the Django values and every Ruby app gets the Rails values. The deploy command of a Python app runs `python manage.py migrate --noinput` when `manage.py` exists, and the deploy command of a Ruby app runs `bin/rails db:prepare` when `bin/rails` exists. The preset also decides the env names of a database, Valkey, and a bucket, and the user has no choice. The section Datastores lists them.

An app pod has no volume. A file that the app writes is gone after the next deploy, and each pod has its own copy. Data that must persist goes into a database or a bucket. Opencloud has no volumes on purpose: a volume allows only one instance and makes each deploy stop the old pod first. A SQLite file in the pod holds only data that may disappear.

In the Laravel preset, BuildKit cache mounts keep the Composer and npm downloads between builds. The web process runs `php artisan optimize` when it starts, because the config cache must see the runtime env.

`App\Domains\Builds\Builder` clones the commit into a temporary folder, writes the Dockerfile, and runs `buildctl` against BuildKit. Build-time env values go in as BuildKit secrets, never as build arguments. BuildKit leaves secret values out of its cache key, so two builds of one commit with other build values would share each layer that read a secret, also between apps and between a preview and production. The builder therefore passes the build argument `OPENCLOUD_BUILD_ENV`, an HMAC of the build values with the app key. The Laravel template declares it in the stages that mount secrets. For a Dockerfile app with build values, the builder builds a copy of the Dockerfile with `ARG OPENCLOUD_BUILD_ENV` after each `FROM`.

`App\Support\SecretMasker` replaces each secret value with `********` in each log line before the line goes into the database.

## Deployments

`App\Domains\Deployments\Enums\DeploymentStatus` is a state machine. Its `canMoveTo()` method lists the allowed moves:

- `queued` to `building`, `failed`
- `building` to `deploying`, `failed`
- `deploying` to `live`, `failed`
- `live` to `superseded`

`App\Domains\Deployments\Jobs\RunDeployment` runs one deployment from start to end. It builds, runs the deploy commands in a Kubernetes Job, applies the manifests, waits for the rollout, and syncs Caddy. If a step fails, the deployment becomes `failed`, and the old live deployment stays live.

`DeploymentStatus::isRunning()` is true for `queued`, `building`, and `deploying`. The dashboard polls while the latest deployment of an environment runs. The deployment page, the canvas, and the deployments tab reload only their `deployment`, `deployments`, `steps`, and `environment` props every 2 seconds, so each status badge moves to `live` or `failed` without a reload. While no deployment runs, the canvas and the deployments tab reload the same props every 10 seconds, because a push, a deploy hook, or another tab can start a deployment that the open page does not know. The hook `useDeploymentPoll` holds both intervals.

### Deployment steps

The enum `App\Domains\Deployments\Enums\DeploymentStep` lists the steps in order. Each step has a phase, `build` or `deploy`, and a title:

| Step | Phase | Work |
|---|---|---|
| `preparing_build` | build | Clone the commit and write the Dockerfile. |
| `running_build` | build | Run `buildctl`. |
| `pushing_application` | build | Copy the image to the registry of the cluster. |
| `preparing_deploy` | deploy | Wait for the datastores, write the env values of each attachment again, and apply the namespace and the env Secret. |
| `running_deploy_commands` | deploy | Run the deploy command Job. |
| `updating_stack` | deploy | Apply the workloads, wait for the rollout, and remove old processes. |
| `routing_traffic` | deploy | Wait for the old pods, move to live, sync Caddy, and check the home page. |

The log holds the steps. `DeploymentLog::step()` appends one marker line, `<ISO time> <U+001E><step value>`, with the same SQL append as the other lines. `DeploymentLog::write()` removes the character U+001E from each output line, so app output cannot write a marker. A step with no work, for example no deploy commands, writes a line that says so. `App\Domains\Deployments\DeploymentSteps::of()` parses the log into a list of steps. Each step has its key, title, phase, status, start time, end time, and lines. A line has its offset in seconds from `started_at`. The status is `finished` when a later step started, `running` for the last step of a running deployment, `failed` for the last step of a failed deployment, and `skipped` for a step that a finished deployment never reached. A log without markers gives one step without a key. The deployment page gets `steps` and no raw log, and it shows the build steps and the deploy steps in two cards.

## Processes

Each environment runs `web` and a list of other processes. Web is special, because it serves HTTP. The environment holds its settings: size, minimum and maximum instances, CPU target, and health path. The readiness probe of web sends the first domain of the environment as the Host header, because an app that checks the host, for example Django with `ALLOWED_HOSTS`, refuses the pod address that the kubelet sends. Each other process is one row in the table `processes`.

| Column | Meaning |
|---|---|
| `environment_id` | The environment. The row goes when the environment goes. |
| `name` | 1 to 30 lowercase letters, digits, and dashes. It starts and ends with a letter or a digit. It is unique in the environment. `web`, `deploy`, and `command` are reserved. |
| `kind` | `long_running` or `scheduled`. `App\Domains\Environments\Enums\ProcessKind` casts it. |
| `command` | A normal command line, for example `php artisan horizon`. |
| `schedule` | A cron expression with five fields, or a shortcut such as `@daily`, for a scheduled process. Null for a long-running process. |
| `size` | The CPU and memory of each pod, with the same sizes as web. |
| `min_instances`, `max_instances`, `cpu_target` | 1 to 20 instances and a CPU target of 10 to 95 percent, for a long-running process. Null for a scheduled process. |

`Process::rules()` and `Process::computeRules()` hold the rules in one place. The actions, the Form Requests, and the create form use them. The rules drop the values that the kind does not use with `exclude_unless`, and `Process::validate()` stores null in their place. So a scheduled process that the sheet sends with instance values keeps no instances. A schedule must also pass `Cron\CronExpression::isValidExpression()`. Kubernetes reads the schedule with robfig/cron, which has no `L` or `W` in the day of the month and no `L` or `#` in the day of the week, so the rules refuse those too.

A new Laravel app gets two rows: `worker`, long-running, with `php artisan queue:work --sleep=3 --tries=3 --max-time=3600`, and `scheduler`, long-running, with `php artisan schedule:work` and exactly 1 instance. `ApplicationType::processes()` returns them. Each new process from the create form takes the size and the CPU target of web, with 1 instance. Node.js, Python, Ruby, static, and Dockerfile apps get no rows, because opencloud does not know their commands. Every app can have its own processes, for example `horizon`, `reverb` with `php artisan reverb:start`, or `ssr` with `php artisan inertia:start-ssr`.

The Laravel scheduler runs `schedule:work` in one long-running process, as Laravel Cloud runs the scheduler in its app instances. The process keeps its pod, so a task with `runInBackground()` finishes, and the `withoutOverlapping()` and `onOneServer()` locks live in the cache of that pod. A rolling deploy starts the new pod before the old pod stops, so two copies can run for a few seconds. A task that must run once uses `onOneServer()` with a cache that the pods share, for example the database or Valkey. The flag `exclusive` is gone, and opencloud has no `Recreate` strategy for a process. The migration `2026_10_27_200001_add_kind_and_scaling_to_processes_table` gives each row the size and the CPU target of its environment. The migration `2026_10_28_200001_run_the_laravel_scheduler_as_a_long_running_process` turns each scheduled row with the command `php artisan schedule:run` and the schedule `* * * * *` into a long-running row with `php artisan schedule:work` and 1 instance. The next deploy of such an app applies the Deployment `scheduler` and deletes the CronJob `scheduler`, because `EnvironmentManifests::strays()` deletes by label.

`EnvironmentManifests` gives each long-running process a Deployment with the name of the process and the label `opencloud.dev/process=<name>`. It has the image, the env Secret, and the size of the process. The container runs the command with `sh -c`, so a normal command line works. A single command gets `exec` in front. Then it is PID 1 and gets the SIGTERM when the pod stops, so a queue worker can finish its job. Dash, the `sh` of Debian images, does not forward the signal. A list, a pipe, or a leading assignment runs without `exec`. A process of a Node.js, Python, or Ruby app sets `args` instead of `command`, so the `tini` entrypoint of the image stays PID 1. The replicas are the minimum instances, and the process uses a rolling update. A process with a maximum above its minimum gets its own HorizontalPodAutoscaler, built like the one of web, and the autoscaler sets the replicas.

`EnvironmentManifests::cronJob()` gives each scheduled process a CronJob with the same name, labels, image, env Secret, size, and command handling. It uses `concurrencyPolicy: Forbid` and `startingDeadlineSeconds: 60`. With `Allow`, a pod that cannot start on a full node does not stop the next run, so on the test machine 60 Pending pods piled up in one hour and would all start at once. `Forbid` keeps one run at a time, and a run that is still busy at the next tick makes the CronJob skip that tick. Each run is one pod with `restartPolicy: Never` and `backoffLimit: 0`. The CronJob keeps one finished Job for success and one for failure. The command of a scheduled process must end, because each run starts a new pod. A task that the command starts in the background ends with the pod. The scheduled kind is for a cron command of any app, for example a cleanup script.

`RunDeployment` waits for the rollout of web and of each long-running process. A CronJob has no rollout to undo, so `RunDeployment` applies the CronJobs only after the rollout succeeds. A failed deployment keeps the old schedule. Then `EnvironmentManifests::strays()` gives one label selector for each Kubernetes kind, and `RunDeployment` deletes the matches:

- each Deployment with an `opencloud.dev/process` label that is not web and not a long-running process,
- each CronJob with the label that is not a scheduled process,
- each HorizontalPodAutoscaler with the label that `EnvironmentManifests::autoscalers()` does not give, so a web or a process with a fixed count loses its autoscaler.

The selectors touch nothing else. So a removed or renamed process stops on the next deploy, and a process that changes kind leaves no object of its old kind. The wait for the old pods leaves scheduled processes out, because the finished pod of the last run keeps the label of an older deployment.

## Actions are the seam between the UI and the engine

Controllers never touch Kubernetes, Caddy, or BuildKit. They validate the request, check the policy, and call one action class in `app/Domains/<Domain>/Actions`. Each action writes the database records, records an audit event, and dispatches jobs. The engine code of each domain, `app/Support/Kube`, and `app/Support/Tofu` runs behind the actions.

## Connected clusters

The owner connects a cluster with its kubeconfig and the address and credentials of a registry near that cluster. `InstallClusterParts` puts Caddy in the namespace `opencloud` with a Service of type `LoadBalancer` and its state on a PVC, and creates the namespace `oc-datastores`. It stores the load balancer address as the ingress IP. Opencloud changes nothing outside its own namespaces, so a cluster that runs other software also works.

For an application on a connected cluster, `RunDeployment` copies the built image from the local registry to the cluster's registry with crane. The environment namespace gets the pull secret `opencloud-registry`, and the pods use the copied image. So a connected cluster can start new pods while the dashboard server is down. The scheduler syncs Caddy only on clusters with the status `ready`.

## Upgrades

`sudo opencloud upgrade [version]` upgrades the server. Without a version, it asks the GitHub releases API of `OPENCLOUD_REPO` for the latest release. It refuses an older release unless you add `--force`. A pre-release such as `v1.2.0-rc.1` is older than `v1.2.0`. Each step prints one line.

1. Download the release archive and check its SHA-256 sum, like the installer. `OPENCLOUD_RELEASE_URL` replaces the GitHub download URL for tests. Nothing has changed yet.
2. Copy the database with `php artisan opencloud:copy-database` in the running dashboard. The command uses `VACUUM INTO`. The copy is `/var/lib/opencloud/data/upgrade-<from>-to-<to>-<time>.sqlite`.
3. Record the images and the rollout revisions of the deployments `dashboard` and `caddy`.
4. Run `install.sh` of the new release with the target version. The upgrade passes on the TLS issuer, the public IP, and the repository from the env of the running dashboard. The image archive variables of the installer pass through. The installer log is `/var/log/opencloud/upgrade-<from>-to-<to>-<time>.log`.
5. Wait for both rollouts and for `/up` through Caddy on port 8000.

If step 4 or 5 fails, the upgrade goes back to the old release. If the dashboard changed, the upgrade scales it to zero. It deletes the write-ahead log and puts back the database copy. Then it runs `kubectl rollout undo` to the recorded revision and scales the dashboard to one.

The upgrade undoes a changed Caddy the same way. Then it waits for `/up` and checks the recorded images. After a way back, the command exits 1.

Caddy uses a rolling update with a 10 second `preStop` sleep, because each release has its own Caddy image tag. The sites keep answering while Caddy changes.

When the new dashboard starts, `opencloud:bootstrap` updates the other clusters. It runs `ReinstallClusterParts` for each cluster that is not `local` and has parts from another release. A cluster with the status `pending` or `installing` keeps its state.

The scheduler runs `CheckLatestRelease` once a day. It caches the tag of the latest release for three days, and a failed request changes nothing. The sidebar shows the running version to each user. When the cached release is newer, it shows the owner the command to run.

`tests/e2e/upgrade.sh` proves an upgrade with no failed request to a live application, and the way back from a release whose dashboard fails.

## Queues

The dashboard pod runs two queue workers. The `worker` container serves the `default` queue with a 600 second timeout. The `builder` container serves the `builds` queue with a 3600 second timeout. Long jobs go on `builds`: `RunDeployment`, `BackupDatabase`, `RestoreDatabase`, `RunRestore`, and the OpenTofu jobs `ProvisionCluster`, `TearDownCluster`, `ProvisionManagedDatabase`, and `TearDownManagedDatabase`. `RunRestore` provisions the datastores itself and waits for no queued job, so it never blocks behind the deployments that it starts. Short jobs stay on `default`: `SyncCaddy`, `CheckDomain`, `ProvisionDatastoreAttachment`, `DeployPush`, `SyncPreview`, `PostPreviewComment`, and `ExecuteCommandRun`. A command can run for 15 minutes, so `ExecuteCommandRun` never waits in the worker. It checks the Job once and releases itself for 3 seconds. A deployment waits for its datastores, so datastore provisioning must never queue behind a deployment.

## Datastores

`App\Domains\Datastores\Provisioners` is the registry of the resources that opencloud attaches. It keys each `Provisioner` on the kind and the source together, so a managed or external attachment never reaches kubectl. The standard source has one provisioner per kind: `LocalMysql`, `LocalPostgres`, `LocalValkey`, and `LocalRustfs`. The abstract `LocalProvisioner` holds the code that the four share: the queue, the status, the job dispatch, and the server rollout. Each kind class holds its own server manifests, names, commands, and connection. `LocalSql` sits between `LocalProvisioner` and MySQL and Postgres. It runs the SQL and the dumps in the server pod, and it is the only `DatabaseDumps`. `ManagedResource` serves the managed source with OpenTofu, and `ExternalProvisioner` serves the external source. A provisioner does the whole lifecycle with `refusalOn()`, `attach()`, `retry()`, `detach()`, `provision()`, `release()`, and `connection()`. The actions and the four datastore jobs make one call to it and do not test the source. `capabilities()` gives one row of the capability table: the dumps of a database or the reason that it has none, whether the nightly job copies the buckets, and why the dashboard does not offer the kind. The nightly backups, `BackupNow`, `RestoreBackup`, and `RestoreInstall` read these capabilities, not a list of kinds. `DatastoreKind::family()` gives the `ResourceFamily`, which sets the name rules, the default of each named family, and the rule of one key-value store per environment. `ProvisionersTest` runs each managed provisioner method with `FakeKubectl`. It also scans the code, so that only the registry creates a local provisioner and only the `Local*` files name `Kubectl`.

MySQL and Postgres run one server per cluster. Each environment gets its own database and user with rights on that database only. RustFS runs one server per cluster with a sidecar container `rc`. Each bucket of an environment gets its own bucket, IAM user, and policy that allows only that bucket. Valkey runs one small instance per attachment. Attach writes the env values with source `datastore`. Detach removes the user or key and keeps the data. `DetachDatastore::destroy()` also removes the data, for previews.

A bucket is private or public. `Provisioner::publicRefusal()` says why an attachment of a kind and source cannot be public, or gives null. Only a RustFS bucket in a cluster with an IPv4 ingress address can be public, because its public address holds that IP. A managed resource stays private, because the `public-read` ACL of Spaces also lets anyone list the files. An external resource keeps the settings that its owner gave it. Each provision of a RustFS bucket sets its anonymous bucket policy again with `rc bucket anonymous`. A public bucket gets a policy that allows `s3:GetObject` on its files and nothing else. A private bucket gets `set private`, so a bucket that became private loses its public read. A detach that keeps the data also sets the bucket private, so no pod in the cluster reads it without a key.

Env names belong to the app framework, not to the resource. A provisioner gives a neutral connection value: `SqlConnection`, `KeyValueConnection`, or `BucketConnection`. An env profile in `app/Domains/Datastores/Env` turns a connection into env values. It has one method for each connection family, and each method is pure. `AttachmentEnv` is the only code that joins a connection to a profile and writes the `env_vars` rows. The preset decides the profiles, and the user has no choice, as on Laravel Cloud ([environments](https://laravel.com/cloud/docs/environments.md), [Node.js](https://laravel.com/cloud/docs/deploy-guides/nodejs.md)). `ApplicationType::envProfiles()` holds the rule. The Laravel preset gets `LaravelProfile`. The Node.js, Python, Ruby, and static presets get `GenericProfile`. The Dockerfile preset gets both, because opencloud cannot know the app in the image, and `AttachmentEnv` merges the two sets. Both sets name the same resource. The only names in both sets are `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_BUCKET`, and `AWS_URL` of a public bucket, with the prefix `<NAME>_` for a bucket that is not the default, and they have the same values. `AttachmentEnvTest` holds this rule. For a database or a bucket that is not the default, a Dockerfile app shows the Laravel config line. A user value with the same key still wins over a datastore value. The migration `2026_10_28_100001` drops the column `env_profile`. Each deploy writes the env values again, so an app whose names changed gets the new names on its next deploy. `LaravelProfile` gives `DB_*` for the default database and `<NAME>_DB_URL` for each other database, `REDIS_*` with `CACHE_STORE=redis` (and `tls://` in `REDIS_HOST` for a store with TLS), `AWS_*` with `FILESYSTEM_DISK=s3` for the default bucket, and `<NAME>_AWS_*` for each other bucket. `GenericProfile` gives `DATABASE_URL`, `<NAME>_DATABASE_URL`, `REDIS_URL`, and the AWS SDK names, with the prefix `<NAME>_` for each bucket that is not the default, like Laravel Cloud does for apps that are not PHP. Both profiles also give `AWS_URL` with the public address of a public bucket. The AWS SDKs have no name for it, so `GenericProfile` uses the Laravel name. `EnvPinTest` holds the Laravel env of every attachment shape against a golden file, `tests/Fixtures/env/laravel.json`. A change to that file changes the env of every deployed Laravel app. `tests/Fixtures/env/dockerfile.json` holds the same shapes for a Dockerfile app.

`ManagedResource` serves the managed source for every kind. It does the whole lifecycle: the refusal, attach, retry, detach, provision, and release. A `ManagedStack` gives the OpenTofu part of one kind. `ManagedDatabase` is the stack for MySQL and Postgres, `ManagedValkey` is the stack for Valkey, and `ManagedBucket` is the stack for a Spaces bucket. `ManagedResources::find()` holds one row per kind with its stack, the right of the DigitalOcean key, the refusal, and the capabilities.

`ExternalResources` serves the external source with `ExternalProvisioner`, for MySQL, Postgres, any server that speaks the Redis protocol, and any S3-compatible bucket. `ExternalConnectionForm` holds the address fields of each family, their rules, and one message per field. `AttachDatastoreRequest` parses the typed input into a connection value at the boundary. The provisioner stores the address on the attachment, in the columns that `of()` reads, and the attachment is ready at once. Each external attachment has its own datastore row without a cluster. It runs no job, no kubectl, and no OpenTofu. Detach deletes the rows and never touches the data. An external attachment has no dumps, so the nightly backup and the install restore skip it. The secret of each family has the request key `password`, so Laravel does not trim it or flash it, and the page never sends it back. An attach with a typed address never reuses an existing attachment. An attachment whose datastore is being destroyed does not count, so a new attach of its family or name makes a new attachment.

An environment has at most one Valkey attachment. It can have more than one MySQL or Postgres database, also two of one kind, and more than one bucket. The database family and the bucket family are named. Each attachment stores its family in `family`. A name has 1 to 30 lowercase letters, digits, and underscores. The name starts with a letter and is unique among the attachments of its family in the environment, so a database and a bucket can both have the name `main`. A database name cannot be a Laravel stock connection (`mysql`, `mariadb`, `pgsql`, `sqlite`, `sqlsrv`), and a bucket name cannot be a Laravel stock disk (`local`, `public`, `s3`), because the line in `config/database.php` or `config/filesystems.php` would replace it. `ResourceFamily::nameError()` holds these rules, and `ResourceFamily::FIRST_NAME` is `main`. `App\Domains\Datastores\DatabaseNames` holds the names of a database on the server, and `LocalRustfs` holds the names of a bucket on the server. The env profile holds the env values. One database and one bucket of an environment are the default of their family. A unique index on `environment_id` and `family` where `is_default` is true keeps each at one.

| Database | Env values |
|---|---|
| The default | `DB_CONNECTION`, `DB_HOST`, `DB_PORT`, `DB_DATABASE`, `DB_USERNAME`, and `DB_PASSWORD`, as before. A Laravel app needs no config. |
| Each other database | One secret value `<NAME>_DB_URL`, for example `REPORTS_DB_URL=postgres://user:password@host:5432/database`. The scheme is `mysql` or `postgres`, because libpq and Node accept only `postgres`. Laravel maps `postgres` to `pgsql`. The user and the password are URL-encoded. |

A Laravel app uses another database with one line in the `connections` of `config/database.php`, for example `'reports' => ['driver' => 'pgsql', 'url' => env('REPORTS_DB_URL')],`. Then it calls `DB::connection('reports')`. The resource sheet shows this line with a copy button.

The database `main` has the database and the user `env_<environment id>`, as each database had before names. Another database has the database `env_<environment id>_<name>`. Its user is `env_<environment id>_` and 8 characters of the SHA-1 of the name, because MySQL allows 32 characters in a user name. A later attach with the same name finds the data again. The attachment keeps its host and its port, so `AttachmentEnv::write()` can write the env values of any attachment again from its row. Attach, the managed apply, and `SetDefaultAttachment` write through it. Each deploy also writes the env values of each attachment again, after the wait for the datastores and before the env Secret, in one transaction. So a deploy always sends the names that the current rule gives, and a stored value from an older rule goes away. The masker of an environment masks each attachment password, plain and URL-encoded, because a database that is not the default has its password only inside its URL.

| Bucket | Env values |
|---|---|
| The default | `FILESYSTEM_DISK=s3`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_DEFAULT_REGION`, `AWS_BUCKET`, `AWS_ENDPOINT`, and `AWS_USE_PATH_STYLE_ENDPOINT`, as before. A Laravel app needs no config. |
| Each other bucket | The same `AWS_*` values with the prefix `<NAME>_`, for example `UPLOADS_AWS_BUCKET`, and no `FILESYSTEM_DISK`. The secret key stays a secret value. |
| A public bucket | Also `AWS_URL` (or `<NAME>_AWS_URL`) with its public address, for example `https://env-7.files.203.0.113.5.sslip.io`. `Storage::url()` reads it. A private bucket has no `AWS_URL`, so the env of each bucket from before visibility stays the same. |

A Laravel app uses another bucket with one disk line in the `disks` of `config/filesystems.php`, for example `'uploads' => ['driver' => 's3', 'key' => env('UPLOADS_AWS_ACCESS_KEY_ID'), ...],`. Then it calls `Storage::disk('uploads')`. The resource sheet shows this line with a copy button. The line of a public bucket also has `'url' => env('UPLOADS_AWS_URL')`.

The bucket `main` has the bucket, the IAM user, and the policy `env-<environment id>`, as each bucket had before names. An S3 bucket name allows no underscore, so another bucket has the bucket, the user, and the policy `env-<environment id>-` and 8 characters of the SHA-1 of the name, like the user of another database. A later attach with the same name finds the data again. A Spaces bucket keeps its random name, and each Spaces bucket has its own datastore row and OpenTofu stack. The nightly copy and the install restore copy every bucket of a RustFS server with its root key, so a second bucket needs no extra step. The migration `2026_10_27_300001` gives each bucket from before names the name `main` and makes it the default, so its names and its env values stay the same.

A rollout ends when the old pods start to stop, but each old pod still answers during its 10 second `preStop` sleep, and Caddy reuses its pooled connections to it. So `RunDeployment` waits up to 60 seconds until the pods of older deployments are gone, and only then marks the deployment live. When a deployment is live, only the new version answers.

Each deployment has its own env Secret, `env-<deployment-id>`. A failed deploy cannot change the env of the pods that still run. After a deployment goes live, the job keeps the live Secret and the two newest, and deletes the rest.

Backups run every night at 03:00. A dump streams through `kubectl exec` into a gzip file under `<data_path>/backups`, or into the S3 backup target when one exists. The newest 7 dumps per attachment stay. A restore first backs up the current state, then empties the database and streams the dump back. A managed database has no dump and no restore here, because DigitalOcean backs it up itself. `BackupNow` and `RestoreBackup` refuse it.

## Restore

A restore puts a lost install back on a new server. The code lives in `app/Domains/Restore`.

1. The owner runs `install.sh` with `OPENCLOUD_RESTORE_FILE`. The file holds the settings of the backup bucket and the saved `APP_KEY`. The installer refuses restore mode when `database.sqlite` exists without `restore.json`.
2. Before the dashboard starts, the installer runs the Job in `platform/restore.yaml` with the dashboard image. The Job reads the file from the host path, so its values never go into a manifest, a Secret, a command line, or a log. It runs `opencloud:fetch-dashboard-backup`. `DashboardBackup` takes the newest `backups/dashboard/*.sqlite.gz` and decrypts one encrypted column with the `APP_KEY`. Only then does it write the `APP_KEY` file and `database.sqlite`. It empties `jobs`, `cache`, and `cache_locks`, because no worker of the lost server lives on. Then `RestoreState::begin()` writes `restore.json` in the data folder with the start time.
3. After the dashboard starts, the bootstrap command stores the new IP as the ingress IP of `local`. The installer runs `opencloud:restore`, which queues `RunRestore` on `builds`.
4. `RestoreInstall` runs the steps of the enum `RestoreStep` in order: retire the old deployments of `local`, provision each attachment again with its stored names and passwords, restore each MySQL and Postgres database, copy the RustFS buckets back, deploy the live commit of each permanent environment, check each domain again, and sync Caddy. `restore.json` records the status of each step. A run skips the done steps, so `opencloud restore` resumes a failed restore.

A database comes back from its newest dump file in the bucket from before the start time. A nightly backup on the new server can dump an empty database during the restore, so later dumps do not count. The dumps of the database `main` are in `backups/<datastore id>/<environment id>`. The dumps of another database are in a subfolder with its connection name, because two databases of one kind share a server. A connected cluster kept running, so the restore leaves its records alone.

## GitHub

`App\Domains\GitHub` is the boundary to GitHub. One `GithubApp` row holds the app of the install. The owner creates it on the page `/settings/github` with the manifest flow. `GitHubClient` signs an RS256 app token with `AppJwt`. It finds the installation of a repository and keeps the installation token encrypted in the cache until one minute before it expires. Tests swap every call with `Http::fake()`.

`App\Domains\Builds\Git` is the only class that runs `git` against a remote. Each call takes the application, and `Git::withRemote()` is the one place that picks the remote. For a github.com repository with the app installed, it uses `https://x-access-token:<token>@github.com/<owner>/<repo>.git`. It fetches the URL directly, so `.git` never stores the token. It masks the token in the message of a failed command. Without a token it uses the plain URL, so public repositories work without the app.

An application can have a deploy key instead of the app. The private key is in the encrypted column `applications.deploy_private_key`, and the public key is in `applications.deploy_public_key`. For a github.com repository with a deploy key, `Git` uses `git@github.com:<owner>/<repo>.git` and sets `GIT_SSH_COMMAND` to `ssh -i <key file> -o IdentitiesOnly=yes -o StrictHostKeyChecking=yes -o UserKnownHostsFile=<pinned file>`. The deploy key wins over the app token. The key file is a temporary file with mode 0600, and `Git` deletes it after the call, also after a failed call. `dashboard/resources/ssh/github_known_hosts` pins the host keys that GitHub publishes, so ssh refuses a server with another key. When GitHub refuses the key, ssh prints `Permission denied (publickey)`, and `Git` throws `DeployKeyRefused`. Its message is the masked git error and the line "GitHub refused the deploy key. Add the public key to the repository under Settings, Deploy keys." The deployment log gets both, and the Deploy button shows the line. The dashboard image has `openssh-client` for `ssh` and `ssh-keygen`.

The create form takes `owner/repo`, the SSH address `git@github.com:owner/repo.git` with or without `.git`, or a full https address. `StoreApplicationRequest::normalizeRepository()` stores each github.com form as `https://github.com/<owner>/<repo>.git`, so `RepositoryName::parse()` reads every one of them.

`App\Domains\Builds\SshKeygen` makes a key pair with `ssh-keygen -t ed25519 -N ''` in a new temporary folder, reads the two files, and deletes the folder. The comment of the key is `opencloud <application name>`. `SshKeygen::keyPairOf()` takes a private key that the user pastes. Laravel trims each form string, and ssh refuses a key file without its last newline, so it adds the newline back. It writes the key to a temporary file with mode 0600, runs `ssh-keygen -y -P '' -f <file>`, and deletes the file in a `finally`. The public key keeps the comment of the key. A key that `ssh-keygen` cannot read, or a key with a passphrase, gives a `ValidationException` on `deploy_private_key`: "Paste an OpenSSH private key without a passphrase." The stored pair has the same shape as a new key, so `Git` treats both the same. The form field `deploy_private_key` is in `dontFlash()`, and the create controller leaves it out of `withInput()`, so the key never reaches the session table. No page prop holds the private key. The application page has a Deploy key section. A user who may change the application adds, replaces, or removes the key there. "Use my own key" opens a field for the private key, and Save sends it to `POST /applications/{application}/deploy-key`. The create form has the same two choices: "Make a new key" and "Use my own key". Each user who may view the application sees the public key and the steps to add it on GitHub, without write access. A push then deploys through the deploy hook of an environment, which GitHub calls as a repository webhook.

`POST /webhooks/github` checks `X-Hub-Signature-256` with `hash_equals` first and answers 401 on a bad signature. It parses the payload into `PushEvent` or `PullRequestEvent`, queues one job, and answers 202. A repeated `X-GitHub-Delivery` id does nothing.

## Previews

A `push` queues `DeployPush`. It deploys the pushed commit to each `permanent` environment of the branch with `auto_deploy` on.

A `pull_request` queues `SyncPreview`. The actions `opened`, `reopened`, and `synchronize` run `App\Domains\Previews\Actions\OpenPreview`. The action `closed` runs `App\Domains\Previews\Actions\ClosePreview`.

- `OpenPreview` skips the pull request when previews are off, or when it comes from a fork and `allow_forks` is off. At `opencloud.max_previews` previews, it comments on the pull request and creates nothing. A new preview is the environment `pr-<number>`. It copies the settings, the processes, and the `user` env values of the preview template, and web runs one instance. It gets its own `APP_KEY` when the template has none, and it attaches the datastores of production. Each attachment is a standard one, also when production uses a managed or external database, because a preview never creates a paid cloud resource and never shares the data of production. Each MySQL or Postgres database keeps its connection name. The default comes first, so it is also the default of the preview. Its domain is `pr-<number>.<preview_domain>`, or `pr-<number>-<application slug>.<ingress ip>.sslip.io` without a preview domain. Then it deploys the head commit.
- `ClosePreview` waits while a deployment of the preview builds or rolls out. Then it deletes the namespace and calls `DetachDatastore::destroy()` for each attachment. It deletes the environment and its records, and it syncs Caddy.
- `DeploymentObserver` queues `PostPreviewComment` when a preview deployment moves to `live`. The job creates one comment with the preview URL and keeps its id in `pr_comment_id`. Later deployments update that comment. A failed call only writes a warning to the log.

## Commands

A user runs a one-off command, for example `php artisan migrate:status`, on an environment. `RunCommand` stores a `CommandRun` with the live deployment. `App\Domains\Environments\Enums\CommandRunStatus` is its state machine. A run moves from `queued` to `running` or `failed`, and from `running` to `succeeded`, `failed`, or `timed_out`.

`ExecuteCommandRun` applies the Job `cmd-<run id>` from `App\Domains\Environments\CommandManifests` in the environment namespace. The Job runs `sh -c <command>` with the image and the env Secret of that deployment, the label `opencloud.dev/process=command`, `backoffLimit` 0, and `activeDeadlineSeconds` 900. Each check reads the Job and copies the pod logs into `output`, with terminal colors removed and secrets masked. So the UI can show the output while the command runs. `Complete` gives `succeeded` with exit code 0. `Failed` gives `failed` with the exit code of the container, or `timed_out` when the reason is `DeadlineExceeded`. When the Job has no end condition 960 seconds after the start, `ExecuteCommandRun` deletes it, and the run becomes `timed_out`. Running a command needs `EnvironmentPolicy::update`. Reading the runs needs the right to read logs.

## Live status

`App\Domains\Environments\LiveStatus` reads what runs now, for the UI to poll. It keeps each answer in the cache for 10 seconds, per environment and per cluster. It makes one kubectl call per resource type, never one per pod. For an environment, it reads the Deployments, the CronJobs, the pods that have not finished, and the pod metrics from `/apis/metrics.k8s.io/v1beta1/namespaces/<ns>/pods`. Each Deployment with the label `opencloud.dev/process` is one entry of `processes`. Each CronJob with the label is one entry of `scheduled`, with the start of the last run from `lastScheduleTime`. The last run failed when no Job of the CronJob runs and `lastSuccessfulTime` is before that start. The process name comes from that label, not from the database. For a cluster, it reads the nodes and the pods of all namespaces that have not finished. `App\Domains\Environments\Quantity` turns Kubernetes quantities such as `250m` and `512Mi` into millicores and MiB. Without a metrics server, the CPU and memory of a process are null. When kubectl fails, the state is `unknown` and the endpoint still answers 200.

## The environment page

The Environment tab is a fixed canvas with three columns: the network, the cluster with the app, and the resources. In the cluster column, the App block shows web, and each process has its own block below it. A long-running block shows the command, the size, the instances, and the ready count. A scheduled block shows the command, the schedule, the size, and the last run. The process sheet has a General tab and, for a long-running process, an Autoscaling tab. It also adds and deletes a process. `EnvironmentController::show` sends the data of every block in one response. Each block opens a side sheet that posts to the existing controllers, so the canvas adds no write endpoint. The page reads `environments.status` every 10 seconds and `clusters.capacity` every 30 seconds with the hook `usePoll`, which stops while the browser tab is hidden. The Commands tab reads the runs and the output of a run with the same hook. The old URLs `/env`, `/domains`, and `/datastores` of an environment redirect to the settings and to the canvas. `EnvironmentController` sends `datastores.offers`, with one offer for each row of `Provisioners::table()` that the environment can still add. An offer has the kind, the source, the family, the name field of a database or a bucket, the label, the menu texts, the refusal for this user and cluster, and the address fields of an external offer. The name field holds the label, the placeholder, the start value, and the dialog text. The first database or bucket of an environment starts as `main`, and a later one starts empty. The add menu renders only this list, so a new registry row needs no TypeScript change. Each database and each bucket is its own card on the canvas, with its name and the Default badge. A node of the canvas is a block, and an edge is a pair of blocks. The `Canvas` component draws the edges as one SVG layer behind the blocks, with one vertical bus in each gap between two columns. Each network block joins the App block, which carries the `target` marker. Each block of the cluster column joins each resource. A block finds its column from the `column` prop of its `Group`, so a new block gets its lines without more code. Hover or focus on a block lights that block, its lines, and the blocks at their other end. Below the `@4xl` width the canvas has one column and no lines. The header of the Environment tab has a Visit site link to the first live domain, and a custom domain comes before the free one. The settings page sends a `resource` name with each env value that a resource sets, for example `Postgres main`. The env section has two modes, Table and Text, and the browser remembers the last mode in `localStorage`. The Text mode is one editor box with line numbers. The locked rows come first: each resource value as its key with "Set by <resource>", and each secret as its key with "Secret". Below them, a textarea with dotenv highlighting (`dotenv-tokens.ts`) holds one `KEY=value` line for each plain user value. `EnvironmentController::settings` sends it as `envText`, which `DotenvText::format()` builds, and "Save values" posts the whole text to `env-text.update`, which calls `SaveEnvText`. The Text mode does not add secrets and does not set "available at". The table still does both.

## Deploy hooks

A deploy hook is a secret URL, `POST /hooks/deploy/<token>`, that starts a deployment of the branch head, for CI. The route is in `routes/webhooks.php`, so it has no session and no CSRF check. It allows 10 requests per minute from one IP address. The token is encrypted in `environments.deploy_hook_token`, so the database cannot look it up. `App\Domains\Deployments\DeployHook::find()` compares the token of each enabled hook with `hash_equals`. A wrong token and a disabled hook both get 404. Only a user who can change the environment sees the URL.

## Default domains

`App\Domains\Routing\DefaultDomain` gives each permanent environment a free address, `<application>-<environment>.<ingress ip>.sslip.io`. sslip.io resolves the IP in the name, so the address needs no DNS step. `CreateApplication` adds it to production when the cluster has an IPv4 ingress address. The command `opencloud:default-domains` adds it to each permanent environment that has no default domain. The domain has `generated` set. Otherwise it is a normal domain. `CheckDomain` checks it, Caddy serves it, and the user can remove it.

Each name is lowercase letters, digits, and dashes. The first label holds at most 63 characters, so a long application name is cut. When another domain already has the name, the application id goes into it, for example `shop-7-production`. The bootstrap command does not run `opencloud:default-domains`, because then a removed default domain comes back after each restart.

## Roles

`App\Domains\Members\Enums\Role` holds the matrix of rights in one place. Policies ask `Role::allows(Ability)` and never compare role names directly. A developer has no write rights on a protected environment.

## Tests

- Each test sits in the folder under `dashboard/tests/` that mirrors its class under `dashboard/app/`, for example `tests/Domains/Deployments/Jobs/RunDeploymentTest.php`.
- Pure classes get tests that assert literal expected values.
- Jobs and controllers get tests with `FakeKubectl`.
- The `Architecture` suite in `dashboard/tests/Architecture` checks the placement, the names, and the dependencies of the classes. Its `baseline.json` lists the old violations. The list can only get shorter.
- The release test in `tests/e2e/` drives a fresh Ubuntu machine. It is the proof of "it just works".
- The deploy matrix in `.claude/skills/verify-opencloud/` deploys one fixture app for each preset on a disposable OrbStack machine. It checks the live HTTPS site after each of three deploys. Each fixture lists the checks that it reports, and the runner prints SKIP for the others. `matrix.py local` builds a fixture with the Dockerfile that `Builder` writes for its preset, and runs it in Docker against MySQL, Postgres, and Valkey, without a machine.

Run the dashboard tests with `XDEBUG_MODE=off php artisan test` in `dashboard/`.
